# Handoffs

**Status: proposed for v0.3. Nothing in this document is implemented yet.**

A contract ([docs/contracts.md](contracts.md)) says ring B reads a file ring A
writes, and `rings contracts` checks whether B's own files name it. That closes
the failure where a handoff is declared and never wired. It leaves open the one
underneath: even when both rings are wired, nobody can say which rows B actually
took, which it refused, which it never saw, and whether the thing B did with a
row can be followed to an outcome anyone would pay for.

A **handoff** is a contract with delivery. The runner, not the agent, carries the
work from one ring to the next, keeps a receipt for every step, and refuses to
publish anything it cannot check. It is the layer that turns a set of loops that
each pass on their own into one system that can be audited end to end.

There is still no process. The spool is a directory. Nothing is running between
ticks, and nothing can be down.

## The problem, precisely

Three things go wrong in a fleet of loops that share files, and a contract
catches none of them:

1. **Lost work.** A producer writes a row. The consumer runs, reads the file,
   crashes or times out before acting, and the next run has no way to know the
   row was never handled. Or the consumer handles it and never records that it
   did, so the run after that handles it again.
2. **False success.** A consumer says it acted. Nothing checks that the thing it
   claims to have done exists anywhere outside its own prose.
3. **Unattributed outcomes.** Money arrives. No one can say which ring's output,
   three handoffs upstream, caused it. Every ring looks equally useful, so none
   can be killed.

Each of these is invisible from inside any one ring. Each ring is individually
healthy. The failure lives in the handoff, so it has to be checked there.

## Five primitives

Everything below is one of these. There is nothing else.

| primitive | what it is | where it lives |
|---|---|---|
| **work item** | one immutable, typed thing handed from one ring to another | `spool/items/<id>/` |
| **delivery** | the state of one work item at one consumer | `spool/deliveries/<ring>/<id>` |
| **run receipt** | exactly what the runner gave an agent and what came back | `<ring>/runs/<run>.receipt` |
| **acceptance gate** | the executable check a candidate must pass to be published | `types/<type>/accept.sh` |
| **outcome** | a work item whose evidence comes from outside the fleet | the last type in a sink's chain |

### Work item

A work item is a domain fact, not a message category. `tender.discovered@1`,
`bid.submitted@1`, `listing.live@1`, `subscription.paid@1`. Generic containers
like "lead" or "artifact" are refused, because a type that means nothing cannot
be checked for anything.

An item is a directory with two files, written once and never edited:

```
spool/items/2026-09-09T15-32-07Z-4f9a1c/
├── manifest          # key=value, one per line; written by the runner
└── payload           # opaque bytes, JSON by convention; written by the agent
```

The manifest is written by the runner, never the agent:

```
id=2026-09-09T15-32-07Z-4f9a1c
type=tender.discovered@1
from=scout
run=2026-09-09T15-30-00Z
ts=2026-09-09T15:32:07Z
key=TED-2026-091234
cause=
ref=https://ted.europa.eu/notice/091234
sha256=9b1c…e0
bytes=1842
```

- `id` is generated by the runner: UTC timestamp to the second plus six hex
  characters. Sortable, unique enough for one machine.
- `key` is the producer's natural key for the fact: a tender number, a store
  listing id, a URL. It is required. A second item with the same `type` and
  `key` is a duplicate and is not published.
- `cause` is the id of the item this one was derived from. It is what makes an
  outcome traceable to its source. Empty only for items that start a chain.
- `ref` is an identifier in a system outside the fleet: a URL, an order id, a
  message id. Optional for most types, required for outcomes.
- `sha256` and `bytes` describe the payload, so a consumer can prove what it
  was given.

The manifest is `key=value` lines on purpose. Bash 3.2 can read it with a `while
read` loop. It contains nothing the runner has to parse out of JSON, and the
payload is never parsed by the runner at all. What the payload means is the
business of the type's acceptance gate, which may use whatever tools it likes.

### Delivery

Publishing an item creates one delivery record per ring that subscribes to its
type. A delivery is the only mutable object in the system, and it moves through
five states:

```
ready ──► leased ──► accepted
             │
             ├──────► rejected
             │
             └──► ready (attempts+1) ──► … ──► dead
```

```
state=leased
attempts=1
leased_by=2026-09-09T16-00-00Z
lease_until=2026-09-09T16:30:00Z
ended=
note=
```

- **ready** — published, waiting for the consumer's next run.
- **leased** — the runner has put this item in front of a running agent. The
  lease expires at the ring's `TIMEOUT` plus five minutes, so a run that dies
  without cleaning up cannot hold an item forever.
- **accepted** — the consumer acted on it, or decided it needed no action, and
  said so. Terminal.
- **rejected** — the consumer decided it does not qualify and said why.
  Terminal. The reason is kept: it is the producer's feedback, and the only
  grade a producer gets that it did not write itself.
- **dead** — leased `MAX_ATTEMPTS` times (default 3) without a decision. Reported
  by `rings doctor`; revived by `rings retry`.

A leased item the agent says nothing about goes back to `ready` with
`attempts+1`. Silence is not acceptance. `attempts` counts leases that ended
without a decision; the prompt shows an item as "attempt N of MAX" where N is
`attempts+1`, and the item is dead when `attempts` reaches `MAX_ATTEMPTS`.

A ring that starts consuming a type sees only items published from that moment
on. The first run that finds no delivery directory for the type writes a
`.since.<type>` marker, and reconciliation ignores older items. Handing an older
item to a new subscriber is a deliberate act: `rings retry <id> <ring>` creates
the `ready` record.

Delivery is **at least once**. An item can be put in front of an agent more than
once, and the design says so instead of pretending otherwise. Publication is
made idempotent by the runner (see Idempotency). Side effects the agent performs
in the world are made idempotent by the runbook, which is told the attempt
number for every item it is given.

### Run receipt

Every run of a ring that emits or consumes writes `<ring>/runs/<run>.receipt`:

```
run=2026-09-09T16-00-00Z
ring=bidder
started=2026-09-09T16:00:00Z
ended=2026-09-09T16:14:31Z
rc=0
verdict=pass
prompt_sha256=…
in=2026-09-09T15-32-07Z-4f9a1c 9b1c…e0 attempt=1
in=2026-09-09T15-40-11Z-77be02 c02a…19 attempt=2
accepted=2026-09-09T15-32-07Z-4f9a1c submitted via portal, ref PRT-88121
rejected=2026-09-09T15-40-11Z-77be02 closes in 2 days, cannot staff
emit=bid.submitted@1 key=PRT-88121 -> 2026-09-09T16-14-30Z-a1e004
invalid=emit bid.submitted@1 key=PRT-88121 duplicate of 2026-09-09T16-14-30Z-a1e004
```

The receipt records what the runner put in the prompt (which items, at which
checksums, on which attempt), the checksum of the whole prompt, and every
decision and candidate that came back, including the ones the runner refused
and why. It proves what the agent was given and what it handed back. It does not
claim to prove what the agent understood.

The ledger line for the run carries the `run` id, so `ledger.jsonl` stays one
line per run and the receipt holds the detail.

### Acceptance gate

The agent writes candidates. The runner decides what is published. Between them
sits the gate.

Built-in checks apply to every candidate, with no configuration:

- the type is declared in `rings.conf`, and this ring's `EMITS` lists it
- `key` is present and no published item of this type has the same `key`
- the payload file exists and is not empty
- if `cause` is given, it names an item that was leased to this run
- if the type is an outcome, `ref` is present

Then, if `$RINGS_HOME/types/<type>/accept.sh` exists and is executable, the
runner calls it with `RING_PAYLOAD`, `RING_KEY`, `RING_REF`, `RING_CAUSE` and
`RING_FROM` in the environment. Exit 0 publishes. Any other exit refuses the
candidate, and the hook's last line of stderr is recorded as the reason.

This is where domain checks belong: the value is numeric and above the bar, the
URL resolves, the closing date is in the future, the listing id exists in the
store, the order id exists in billing. The hook may use `jq`, `node`, `curl`,
`python3`, anything installed. The core of `rings` stays dependency-free by
never opening the payload itself.

A declared type with no gate is reported by `rings doctor` as `[ungated]`. It
still works. It is just a type whose items are accepted on the producer's word,
and the report exists so that is a choice and not an oversight. For an outcome
type it is the finding to fix first: an ungated outcome is an apex that moves on
an agent's say-so, which is the thing this whole layer exists to prevent.

### Outcome

An outcome is a work item of the last type in a sink's chain. It is the only
kind of item that moves the apex, and it has one extra rule: its evidence must
come from outside the fleet. `ref` is required, and the gate for an outcome type
should verify that reference against the system it points at.

An agent writing "contract signed" into a deliverable moves nothing. An item of
type `contract.signed@1` with `ref=` pointing at an award notice, published by a
ring whose job is to watch for award notices, passing a gate that fetched that
notice, moves the funnel by one.

## Declaring

In `rings.conf`, each sink now names its chain: the types that feed it, in
order, ending in the outcome.

```bash
APEX="signed work, and nothing that does not lead to it"
SINKS="revenue:Money in, proof:Machine still verified"

CHAIN_revenue="tender.discovered@1 bid.submitted@1 contract.signed@1"
CHAIN_proof="sweep.ran@1"
```

Order in the chain is documentation and the funnel's column order. The funnel
itself is derived from `cause` links, not from this line.

In `ring.conf`, the existing keys gain a second form. An entry containing `@` is
a handoff type; an entry of the form `producer.name` is a v0.2 file contract, and
both kinds keep working side by side.

```bash
# scout/ring.conf
EMITS="tender.discovered@1"

# bidder/ring.conf
CONSUMES="tender.discovered@1"
EMITS="bid.submitted@1"
MAX_ATTEMPTS=3      # default 3
INBOX_MAX=10        # default 10; items per run, oldest first
```

`SERVES` is no longer needed for a ring that emits a chained type: the sink
follows from the type. It stays for rings that hand off nothing.

A type consumed by no ring is published anyway and reported `[orphan]`, the
same finding a v0.2 contract gets. A `CONSUMES` naming a type no chain declares
is `[dangling]`.

## What the agent sees

The runner clears `in/`, `out/handoffs` and `out/emit/` before the agent
starts, for the same reason it deletes the deliverable: last run's output must
not be able to pass as this run's.

It then appends one block to the prompt, after the runbook and the existing
context:

```
HANDOFFS

Inbox: 2 item(s) leased to this run. Payloads are in in/.
  2026-09-09T15-32-07Z-4f9a1c  tender.discovered@1  from scout  attempt 1 of 3  in/2026-09-09T15-32-07Z-4f9a1c.json
  2026-09-09T15-40-11Z-77be02  tender.discovered@1  from scout  attempt 2 of 3  in/2026-09-09T15-40-11Z-77be02.json

An item on attempt 2 or more was put in front of a previous run that did not
decide it. Before repeating any action in the world for such an item, check
whether that action already happened.

Decide every item. Write one line per decision to out/handoffs:
  accept <id> <note>         you acted on it, or it needed no action
  reject <id> <reason>       it does not qualify; the reason goes back to the producer
An item you write nothing about returns to the queue and counts as an attempt.

To hand work on, write the payload to a file under out/emit/ and add one line:
  emit <type> key=<natural key> [cause=<inbox id>] [ref=<external id or URL>] file=<path>
You may emit: bid.submitted@1
```

`out/handoffs` is whitespace-separated tokens with `key=value` pairs, one
decision per line. It is the one format that both an agent and bash 3.2 write
and read without a parser. A line the runner cannot parse is recorded in the
receipt as `invalid` and reported by `rings doctor`; it never becomes an item.

Only complete lines (ending in a newline) are processed, so a run killed at the
timeout cannot publish half a candidate.

## What the runner does

Before the agent:

1. **Reconcile.** For every item of a type this ring consumes, make sure a
   delivery record exists (see Failure and repair). Return every lease past
   `lease_until` to `ready` with `attempts+1`, or to `dead` if that reaches
   `MAX_ATTEMPTS`.
2. **Lease.** Take up to `INBOX_MAX` `ready` deliveries, oldest first. Mark each
   `leased` with this run's id and `lease_until`. Copy each payload to `in/`.
   Record each id, checksum and attempt in the receipt.
3. **Prompt.** Append the block above.

After the agent, in this order:

4. **Publish candidates.** For each complete `emit` line: build the manifest,
   run the built-in checks and the type's gate, then write the item to
   `spool/incoming/<id>/` and `mv` it to `spool/items/<id>/`. Rename within one
   filesystem is atomic; an item is either entirely there or entirely absent.
   Then create a `ready` delivery for every subscriber.
5. **Apply decisions.** For each `accept` or `reject` naming an id leased to this
   run, move the delivery to that terminal state with the note. A decision
   naming an id not leased to this run is `invalid`.
6. **Release the rest.** Every id leased to this run and not decided goes back
   to `ready` with `attempts+1`, or to `dead`.
7. **Receipt and ledger.** Write the receipt; append the ledger line with the
   run id and the counts.

Publishing before applying decisions is deliberate. If the runner dies between
steps 4 and 5, the emitted items exist and the input goes back to `ready`; the
next run sees attempt 2, checks the world, finds the work done, and accepts. If
the order were reversed, a crash would accept the input and lose the output,
which is the unrecoverable direction.

## Idempotency

Two layers, one honest boundary between them.

**Publication is idempotent, and the runner owns it.** `type` plus `key` is the
identity of a fact. A candidate whose `type` and `key` match a published item is
refused as `duplicate of <id>` and recorded in the receipt. A retried run that
re-emits the same bid produces no second item.

**Side effects are idempotent only if the runbook makes them so.** The runner
cannot un-submit a bid or un-send a message. What it can do is tell the agent,
in the prompt, that an item is on attempt 2, and make `ref` available so a
runbook can say "check the portal for this reference before submitting". A
consumer that performs actions in the world should record the external
reference in its `accept` note or in the payload it emits, so the next attempt
has something to check.

## What "cannot fake" means here

The agent and the runner execute as the same user on the same machine. The
agent could, in principle, write to the spool directly. Nothing in this design
prevents that, and nothing here should be described as tamper-proof.
Cryptographic signatures on manifests would be theater under that execution
model, and are not proposed.

What the design does is narrower and real: **the agent never controls the
evidence about its own work.** Identity, time, provenance, checksums and
delivery state are written by the runner. The agent's only channel is a candidate
in `out/`, and a candidate becomes a fact only by passing checks the agent did
not write. Whether a consumer took a producer's item is recorded by the
consumer's runner, not the producer's prose. Whether an outcome happened is
established by a `ref` into a system outside the fleet, checked by a gate.

Call it runner-verified. It is a large step up from a ledger of self-reports, and
it stops exactly where it stops.

## Commands

```
rings emit <ring> <type> key=<k> [cause=<id>] [ref=<r>] --file <payload>
                              publish from a script or by hand; same gate as an agent run
rings inbox <ring>            what is waiting for a ring: ready, leased, attempts
rings trace <id>              one item's whole life: producer run, every delivery,
                              every decision, everything emitted with it as cause,
                              back to the source and forward to the outcome
rings handoffs [--json]       per type: items, ready, leased, accepted, rejected, dead
rings retry <id> [<ring>]     dead → ready with attempts reset; creates the
                              delivery if the ring never had one
rings goals                   now also prints the funnel per sink, from cause links
```

`rings goals` with a chain declared:

```
apex: signed work, and nothing that does not lead to it

  revenue — Money in
      tender.discovered@1   41   scout
      bid.submitted@1        6   bidder
      contract.signed@1      0   closer
```

Counts are published items per type, in chain order. `rings trace` shows the
`cause` path for any one of them; the funnel says how many, the trace says which.

`rings emit` exists so that a producer does not have to be an agent. A scraper
written in any language publishes by calling it, and gets the same gate, the
same manifest, and the same duplicate check as a ring run.

## Doctor

Added to `rings doctor`, next to the existing findings:

| finding | meaning |
|---|---|
| `[undelivered]` | an item exists with no delivery record for a subscriber; reconciled on the subscriber's next run, reported until then |
| `[backlog]` | a ring has `ready` items older than its schedule interval times three |
| `[dead-letter]` | items that reached `MAX_ATTEMPTS`; each one is work the fleet dropped |
| `[invalid]` | a ring's last 20 receipts include candidates or decisions the runner refused |
| `[ungated]` | a declared type has no `accept.sh` |
| `[orphan]` | a type is emitted and no ring consumes it (same finding as v0.2) |
| `[dangling]` | a ring consumes a type no chain declares |

## Failure and repair

The spool is designed to be repaired by hand with `ls`, `cat` and `mv`, because
that is what will actually happen at 3am.

- **Crash before publish.** Nothing in the spool. Input items return to `ready`
  when their lease expires. Attempt count goes up.
- **Crash between publish and deliveries.** Item exists, some subscribers have no
  record. Reconciliation at each subscriber's next run creates the missing
  `ready` record. `[undelivered]` reports it meanwhile.
- **Crash between publish and decisions.** Covered above: outputs exist, inputs
  return to `ready`, attempt 2 checks the world.
- **Agent writes garbage.** Refused, recorded as `invalid`, nothing published.
- **Duplicate emit.** Refused as duplicate, recorded, nothing published.
- **Item dead-lettered wrongly.** `rings retry <id>`.
- **Payload corrupted on disk.** `sha256` in the manifest disagrees; `rings trace`
  says so and the item is not leased.

No state is derived from file modification time anywhere in this layer. Every
transition writes the time it happened.

## Layout

```
$RINGS_HOME/
├── rings.conf                    APEX, SINKS, CHAIN_<sink>
├── types/
│   └── tender.discovered@1/
│       └── accept.sh             optional gate
├── spool/
│   ├── incoming/                 staging; items are mv'd out of here atomically
│   ├── items/<id>/manifest
│   ├── items/<id>/payload
│   └── deliveries/<ring>/<id>    one mutable record per item per consumer
└── <ring>/
    ├── in/                       payloads leased to the current run
    ├── out/handoffs              the agent's decisions and emit lines
    ├── out/emit/                 payloads the agent wants published
    └── runs/<run>.receipt
```

## Requirements

Nothing new beyond what `rings` already asks for, plus `shasum` or `sha256sum`
for payload checksums. Both ship with macOS and every mainstream Linux. The
runner never needs a JSON parser; only gate hooks might, and each gate states
its own needs.

## Testing

All of it runs from `test/smoke.sh` with fake shell agents, no API key and no
network, under bash 5 and `/bin/bash` 3.2:

- publish, lease, accept: one item moves `ready → leased → accepted`, receipt
  and manifest match
- reject with reason: reason is readable from `rings trace`
- silence three times: `attempts` reaches 3, state is `dead`, doctor reports it,
  `rings retry` revives it
- duplicate `key`: second candidate refused, first item untouched
- undeclared type, missing key, unreadable line: each refused and recorded
  `invalid`, nothing in `spool/items`
- crash simulation: a lease with `lease_until` in the past is reclaimed on the
  next run with `attempts+1`
- missing delivery record: created by reconciliation, `[undelivered]` clears
- timeout mid-write: a partial last line in `out/handoffs` is ignored
- `cause` naming an item not leased to this run: refused
- three-ring chain: scout emits, bidder consumes and emits with `cause`, closer
  emits an outcome with `ref`; `rings trace` walks the whole path and
  `rings goals` shows 1 / 1 / 1
- `rings emit` from a plain script produces an item indistinguishable from one
  emitted by a ring run

`examples/handoff-demo` ships those three rings with fake agents, so a fresh
clone can watch one fact travel to an outcome without spending anything.

## Left out of v1 on purpose

Each of these is a real feature and each is a future requirement being invented
in advance. None is needed to make one handoff impossible to lose and one
outcome impossible to counterfeit, which is what v1 has to prove.

- broadcast to undeclared consumers, and any routing beyond "the rings whose
  `CONSUMES` names this type"
- row filters (`key=value`); a type that needs a filter is two types
- request/reply, `reply_to`, and generic `task` / `result` / `ask` types
- expiry on items; a consumer that finds an item too old rejects it and says so
- a defer state; silence already returns an item to the queue
- retry policies beyond a fixed `MAX_ATTEMPTS`
- a schema registry; the gate hook is the schema
- the human as a ring with an inbox; a later version, once the mechanics have
  carried real work
- waking a ring early because work is waiting; rings run on their schedule
- any dashboard; `rings handoffs --json` and `rings trace` are the interface

## Relationship to contracts

v0.2 file contracts stay. Some handoffs are genuinely a file: a report a human
reads, a state file a bot polls. `rings contracts` keeps checking those. A
handoff is the right tool when a downstream ring is expected to act on
individual items and someone needs to know, per item, whether it did. Moving a
contract to a handoff means: declare the type in a chain, change `EMITS` and
`CONSUMES` to the type form, have the producer write `emit` lines instead of
appending to the carrier, and stop reading the carrier in the consumer's
runbook. Both can run in parallel while that happens.
